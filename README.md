# CommonTime

CommonTime is a small group-scheduling application. One person creates a poll with
candidate dates, a time range, and a slot length, then shares the generated link.
Participants enter their name and mark available time slots using click or
click-and-drag. CommonTime combines the responses into a group availability grid,
a participant list, and a ranked list of the best overlapping times.

The existing React pages, components, styling, and interactions are preserved.
Persistence now runs through an Express API and a MySQL database instead of browser
storage. The browser only remembers the current user's display name locally so a
returning participant can reopen their saved response conveniently.

## Technology stack

| Layer | Technology |
| --- | --- |
| Frontend | React 18, React Router 7, Vite 5, Tailwind CSS 3 |
| Backend | Node.js 22, Express 4 |
| Database | MySQL 8.4.3, InnoDB, `mysql2/promise` |
| Containerization | Docker, multi-stage Dockerfile, Docker Compose |
| Configuration | `.env` / environment variables, `dotenv` |
| Optional database UI | Adminer 4.8.1 (`tools` Compose profile) |

## Architecture

```text
Browser
  │
  │ HTTP :3000
  ▼
┌──────────────────────────────────────────────┐
│ app container (Node.js / Express)            │
│                                              │
│  Express static middleware ──► built `dist/` │
│  Express API                                 │
│    /health                                   │
│    /api/polls...                             │
└───────────────────┬──────────────────────────┘
                    │ mysql2 pool, TCP :3306
                    ▼
┌──────────────────────────────────────────────┐
│ mysql container (mysql:8.4.3)                │
│   database: commontime                       │
│   named volume: commontime_mysql_data        │
└──────────────────────────────────────────────┘
                    ▲
                    │ optional `tools` profile
             ┌──────┴──────┐
             │ Adminer     │
             │ host :8080  │
             └─────────────┘
```

The Compose stack uses a user-defined bridge network. The app reaches MySQL by the
service name `mysql`; MySQL is not required to be exposed to other hosts. The
`mysql` service publishes port `3307` on the host by default, which is convenient
for running the API locally with `npm run server`. The application itself is
published on port `3000`.

The production Dockerfile has two stages:

1. `builder` installs all dependencies and runs `vite build`.
2. `runtime` installs production dependencies only, copies `server/` and the built
   `dist/`, and runs the Express server as the unprivileged `node` user.

The builder stage contains the full dependency set needed to compile the frontend.
The final runtime stage starts from the base image again and includes only
production dependencies, the server, and the built frontend. This keeps build-only
dependencies and source files out of the final runtime image.

### Docker Compose

`docker-compose.yml` defines the `app` and `mysql` services on the
`commontime_network` bridge network. The app connects to MySQL using the Compose
service name `mysql`, and starts only after the MySQL healthcheck passes. The
database stores its files in the named `mysql_data` volume, which is preserved by
`docker compose down`. Adminer is optional and is enabled with the `tools` profile.
Port mappings and database settings are configured through `.env` (created from
`.env.example`).

Express serves both the SPA and the API in production, so the frontend and backend
share an origin. During local development Vite proxies `/api` and `/health` to the
Express server on port `3000`.

## Features preserved

- Create a poll with an event title, optional description, date range or selected
  dates, time range, and 15/30/60-minute slots.
- Unique shareable poll links.
- Name-only participation; names are matched case-insensitively per poll.
- Click and click-and-drag availability selection.
- Editing an existing participant's availability by reloading or re-entering the
  same name.
- Group availability grid with overlap counts, best-slot highlighting, and
  per-participant inspection.
- Ranked scheduling results.
- Existing pages, components, styling, and interactions remain in place.

## Database schema

The schema is applied from [`database/init.sql`](database/init.sql) the first time
the MySQL volume is created.

```text
polls 1 ─────── * participants 1 ─────── * availability
```

### `polls`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `VARCHAR(16)` | Primary key; generated by the server |
| `title` | `VARCHAR(100)` | Required |
| `description` | `VARCHAR(500)` | Optional |
| `dates` | `JSON` | Sorted array of `YYYY-MM-DD` dates (at most 60) |
| `start_time` | `TIME` | Poll start time |
| `end_time` | `TIME` | Poll end time |
| `interval_minutes` | `SMALLINT UNSIGNED` | `15`, `30`, or `60` |
| `created_at` | `DATETIME(3)` | UTC timestamp |

### `participants`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `VARCHAR(16)` | Primary key; generated by the server |
| `poll_id` | `VARCHAR(16)` | Foreign key to `polls.id`, `ON DELETE CASCADE` |
| `name` | `VARCHAR(50)` | Display name |
| `name_key` | `VARCHAR(50)` | Trimmed/lower-cased name for duplicate detection |
| `created_at` | `DATETIME(3)` | UTC timestamp |
| `updated_at` | `DATETIME(3)` | Updated when availability changes |

A unique key on `(poll_id, name_key)` prevents duplicate participants in the same
poll. A unique key on `(id, poll_id)` supports the composite foreign key below.

### `availability`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | Auto-increment primary key |
| `poll_id` | `VARCHAR(16)` | Foreign key to `polls.id`, `ON DELETE CASCADE` |
| `participant_id` | `VARCHAR(16)` | Participant reference |
| `slot_date` | `DATE` | Slot date |
| `slot_time` | `TIME` | Slot start time |
| `created_at` | `DATETIME(3)` | UTC timestamp |

The composite foreign key `(participant_id, poll_id)` references
`participants(id, poll_id)`, guaranteeing that an availability row cannot point at
a participant from a different poll. A unique key on
`(participant_id, slot_date, slot_time)` prevents duplicate slots per participant.
Deleting a poll cascades to its participants and availability rows.

## API

Base URL in the complete Docker stack: `http://localhost:3000`.

All request and response bodies use JSON. Errors have this shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Enter an event title."
  }
}
```

### `GET /health`

Checks the API process and database connectivity. Returns `200` when MySQL is
reachable, or `503` when the database check fails.

```json
{
  "status": "ok",
  "database": "up",
  "timestamp": "2026-11-09T10:00:00.000Z"
}
```

### `GET /api/polls`

Returns the 100 most recent polls, newest first. Each poll includes
`participantCount`.

```json
{
  "polls": [
    {
      "id": "b07254672519",
      "title": "Team Meeting",
      "description": "Find a weekly slot",
      "dates": ["2026-12-01", "2026-12-02"],
      "startTime": "09:00",
      "endTime": "10:00",
      "interval": 30,
      "createdAt": "2026-11-09T10:01:13.733Z",
      "participantCount": 2
    }
  ]
}
```

### `POST /api/polls`

Creates a poll. Returns `201 Created` with `{ "poll": ... }`; validation failures
return `400`.

```json
{
  "title": "Team Meeting",
  "description": "Find a weekly slot",
  "dates": ["2026-12-01", "2026-12-02"],
  "startTime": "09:00",
  "endTime": "10:00",
  "interval": 30
}
```

Validation rules: title required and at most 100 characters; description at most
500 characters; 1–60 unique valid dates; `HH:MM` start/end with end after start;
interval must be 15, 30, or 60; the range must fit at least one slot.

### `GET /api/polls/:id`

Returns `200` with `{ "poll": ... }`, or `404` if the poll does not exist.

### `GET /api/polls/:id/participants`

Returns `200` with `{ "participants": [...] }`. Each participant includes their
saved slots in `YYYY-MM-DD|HH:MM` form, sorted by date/time.

```json
{
  "participants": [
    {
      "id": "99bc8b62a0fd",
      "name": "Alice Example",
      "slots": ["2026-12-01|09:00", "2026-12-01|09:30"],
      "createdAt": "2026-11-09T10:01:20.000Z",
      "updatedAt": "2026-11-09T10:01:25.000Z"
    }
  ]
}
```

Returns `404` if the poll does not exist.

### `POST /api/polls/:id/participants`

Adds a participant or returns the existing participant with the same normalized
name. A new participant returns `201`; a duplicate returns `200`; invalid names
return `400`; a missing poll returns `404`.

```json
{
  "name": "Alice Example"
}
```

```json
{
  "participant": {
    "id": "99bc8b62a0fd",
    "name": "Alice Example",
    "slots": [],
    "createdAt": "2026-11-09T10:01:20.000Z",
    "updatedAt": "2026-11-09T10:01:20.000Z"
  },
  "created": true
}
```

### `GET /api/polls/:id/availability`

Returns aggregate availability for every slot in the poll, including slots with
zero responses.

```json
{
  "availability": {
    "pollId": "b07254672519",
    "participantCount": 2,
    "dates": ["2026-12-01", "2026-12-02"],
    "times": ["09:00", "09:30"],
    "bestCount": 2,
    "slots": [
      {
        "date": "2026-12-01",
        "time": "09:00",
        "count": 2,
        "participantIds": ["99bc8b62a0fd", "797e47f7b697"],
        "participantNames": ["Alice Example", "Bob O'Brien"]
      }
    ]
  }
}
```

Returns `404` if the poll does not exist.

### `POST /api/polls/:id/availability`

Replaces all availability for one participant in a single transaction, then
returns the updated participant. An empty `slots` array clears the participant's
availability. Invalid slot keys or slots outside the poll schedule return `400`;
a missing poll or participant returns `404`.

```json
{
  "participantId": "99bc8b62a0fd",
  "slots": ["2026-12-01|09:00", "2026-12-01|09:30"]
}
```

```json
{
  "participant": {
    "id": "99bc8b62a0fd",
    "name": "Alice Example",
    "slots": ["2026-12-01|09:00", "2026-12-01|09:30"],
    "createdAt": "2026-11-09T10:01:20.000Z",
    "updatedAt": "2026-11-09T10:01:30.000Z"
  },
  "savedCount": 2
}
```

All SQL uses parameterized statements with bound/escaped values, including the
dynamic bulk insert used when replacing availability. Request bodies, names,
dates, times, intervals, participant IDs, and slot keys are validated before
database work.

## Installation

### Prerequisites

- Node.js 20 or newer (Node.js 22 is used in the container).
- npm.
- Docker Desktop / Docker Engine with Compose v2.
- Ports `3000` and `3307` available (and `8080` if Adminer is used).

### Environment variables

Create a local `.env` from the example:

```bash
cp .env.example .env
```

PowerShell equivalent:

```powershell
Copy-Item .env.example .env
```

| Variable | Default | Purpose |
| --- | --- | --- |
| `APP_PORT` | `3000` | Host port for the application |
| `ADMINER_PORT` | `8080` | Host port for Adminer |
| `MYSQL_HOST_PORT` | `3307` | Host port mapped to MySQL for local API development |
| `MYSQL_ROOT_PASSWORD` | example value | MySQL root password |
| `DB_NAME` | `commontime` | Database name |
| `DB_USER` | `commontime` | Application database user |
| `DB_PASSWORD` | example value | Application database password |
| `DB_HOST` | `127.0.0.1` | Host used by `npm run server` outside Docker |
| `DB_PORT` | `3307` | MySQL host port used outside Docker |

Change the example passwords before using this outside a local exercise. The
Compose app service overrides `DB_HOST` to `mysql` and `DB_PORT` to `3306` so the
same `.env` works for both local development and containers.

### Run the complete Docker stack

```bash
docker compose up -d --build
```

Open `http://localhost:3000`.

Check service health:

```bash
docker compose ps
curl http://localhost:3000/health
```

Start the optional Adminer database UI:

```bash
docker compose --profile tools up -d
```

Open `http://localhost:8080`. Log in with:

- System: `MySQL`
- Server: `mysql`
- Username: value of `DB_USER` (`commontime` by default)
- Password: value of `DB_PASSWORD`
- Database: value of `DB_NAME` (`commontime` by default)

### Run locally with Vite

Start only MySQL in Docker:

```bash
docker compose up -d mysql
```

Install dependencies:

```bash
npm install
```

Run the API in one terminal:

```bash
npm run server
```

Run Vite in a second terminal:

```bash
npm run dev
```

Open `http://localhost:5173`. Vite proxies `/api` and `/health` to the Express
server on `http://127.0.0.1:3000`.

### Production build without Docker

```bash
npm run build
npm start
```

`npm start` serves the built SPA and API on `http://localhost:3000`.

## Docker commands

```bash
# Build and start app + MySQL in the background
docker compose up -d --build

# Show service state and health
docker compose ps

# Follow logs from all services, or one service
docker compose logs -f
docker compose logs -f app
docker compose logs -f mysql

# Restart without deleting the MySQL named volume
docker compose down
docker compose up -d

# Start the optional Adminer profile
docker compose --profile tools up -d

# Stop containers and remove the named database volume and all data
# (use --profile tools as well if Adminer is still running)
docker compose down -v
docker compose --profile tools down -v

# Open a MySQL shell inside the database container
docker compose exec mysql mysql -ucommontime -p commontime
```

The MySQL data is stored in the named volume `commontime_mysql_data`.
`docker compose down` preserves it; `docker compose down -v` removes it. The next
`docker compose up` after `down -v` recreates the volume and runs
`database/init.sql` again.

## Testing

Start the app or the local API, then run the repeatable API smoke suite:

```bash
npm run test:api
```

The suite checks:

- `GET /health` returns `200` and reports the database as up.
- Poll listing and creation.
- Input validation and malformed JSON handling.
- Poll lookup and `404` behavior.
- Participant creation, case-insensitive duplicate handling, and name validation.
- Availability creation and replacement.
- Invalid-slot and missing-participant errors.
- Availability aggregation, overlap counts, and participant names.
- API `404` handling for unknown endpoints.

The complete frontend workflow was also verified with Playwright against both the
Vite development proxy and the production Express build: poll creation, share
links, drag selection, saved-name restoration, adding a second participant in a
separate browser context, editing availability, group grid counts, individual
participant inspection, ranked results, and the poll-not-found view.

Docker persistence was verified by creating poll `b20f71a54826`, running
`docker compose down`, starting again with `docker compose up -d`, and confirming
that the poll remained available from `GET /api/polls`. A direct MySQL query also
confirmed the poll row and its stored fields. This verifies the poll persistence
case; it does not claim a separate restart test for participant/availability data
or a `docker compose down -v` volume-removal test.
